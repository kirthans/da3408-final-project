## 2. How they were used

**Design (2026-10-26 to 2026-11-15).**
- The student set the requirements and made the major product and scope decisions:
  - static HTML/JS frontend (U1);
  - a gradient-boosted model, later without the GRU challenger because of the deadline (U2, D24);
  - the 2020 "pandemic replay" as the production stream (U3);
  - no Kubernetes (U4);
  - sample sizes (D21), no automatic git commits from the trainer (D22), lean scope (D26);
  - SSH DVC remote instead of MinIO (D27), reduced Stockfish budget (D28), drift thresholds and the disclosed drift-injection switch (D30).
- Claude proposed options with alternatives and trade-offs for each technical decision (D1–D30), written as decision records tied to the course lectures. The student accepted, changed or rejected each one.
- **[student]** Describe in your own words which trade-offs you weighed yourself and where you changed Claude's proposal (for example D21, D26, D27, D28, D30).

**Implementation (2026-11-15 to 2026-11-18).**
- The approved design was split into milestones M1–M9. For each one, Claude wrote a delegation brief: scope, constraints and acceptance criteria. The briefs are kept in the project journal (see §5).
- Codex implemented each milestone, ran the tests and reported back.
- Claude reviewed every milestone by reading the code and re-running the checks and drills itself. It then sent fixes back to Codex. The fix rounds are recorded in the project journal (see §5).
- **No metric, log or dashboard in this repository was written by hand or invented by an AI.** Every number comes from running the real pipeline, services and tests on the Lichess data (`reports/*.json`, `reports/tests.xml`, MLflow runs, Prometheus).
- **AI-generated PromQL:** every alert expression in `infra/prometheus/rules.yml` carries a comment with the prompt used to produce it, as the course requires.

**Debugging.**
- Errors from failed runs (Docker networking, DVC run-cache behaviour, a UID lookup crash in the trainer container, Spark/Ray resource limits) were diagnosed by Codex and Claude from the real logs.
- Each issue is recorded with its root cause in the project journal (see §5).

**Documentation.**
- Claude drafted `DESIGN.md`, `docs/architecture.md`, `hld.md`, `lld.md`, `test_plan.md` and `user_manual.md`, plus the journal.
- `docs/test_report.md` is generated by a script from the real test output.
- **[student]** List anything you rewrote or added yourself (the report, the videos, the diagrams).

## 3. Review and accountability

- Gate reviews: the student reviewed the system at four gates (A: data pipeline, B: training and serving, C: monitoring and retraining, D: console, tests, docs). A written report with a code walkthrough and checklist was produced for each gate (kept in the project journal, see §5).
- Security-relevant settings were reviewed explicitly:
  - secrets only in the gitignored `.env`;
  - the API key on the retrain endpoints;
  - monitoring ports bound to localhost;
  - upload size cap;
  - TLS on nginx;
  - no personal paths in committed files.
- **[student]** Confirm: "I have reviewed the code and configuration and can explain, modify and troubleshoot every part of it, including the orchestration pipeline, data versioning and model tracking."

## 4. Impact

- AI tools wrote nearly all of the code and documentation text, which made a project of this scope possible within the course deadline.
- The architecture, the scope cuts and the evaluation criteria came from design discussions in which the student made the decisions. These are recorded with dates in the decision log.

## 5. Where the records are

The design and process records are kept by the student and are available to the instructors on request. They are not part of this repository (the student's choice):
- `DECISIONS.md`: every design decision, with options, rationale and who decided.
- `JOURNAL.md`: a timestamped log of every discussion, delegation, review and result.
- The delegation briefs: the exact tasks given to Codex, and its reports.

Committed evidence that reflects them: `DESIGN.md` (the approved design with its decision IDs and change sections §19–§24) and the alert-rule prompt comments in `infra/prometheus/rules.yml`.
